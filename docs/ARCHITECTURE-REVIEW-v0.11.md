# Architecture review v0.11

Audit date: 2026-09-06. This audits the v0.10 baseline at commit d0954e1, before the v0.11 changes. For implementation status and validation, see [ITERATION-v0.11.md](ITERATION-v0.11.md). The initial audit itself did not run Unity. The active build scene is `Assets/RiskAI/Scenes/LasMarcas.unity`; it creates the battlefield, towns, units, naval world, camera, and HUD at runtime from `RiskBootstrap`.

The review identifies the main dependencies to remove before a networked or larger simulation. This baseline audit distinguishes existing behavior from proposed migrations; the iteration note records what v0.11 implements.

## Claim audit

| Review point | Finding | Evidence and consequence |
|---|---|---|
| Fixed 20 Hz simulation clock, with pause independent of global `timeScale` | **Valid, high priority** | `BattleSession.Update` advances battle time and economy from variable `Time.deltaTime` and pauses by writing `Time.timeScale` ([BattleSession.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/BattleSession.cs#L69)). Soldiers, settlements, ships, towers, and effects also use `Update`, `Time.time`, or `Time.deltaTime` ([Soldier.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/Soldier.cs#L135), [Settlement.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/Settlement.cs#L146), [Ship.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/Ship.cs#L84)). Implement a simulation accumulator/tick and a local pause gate before adding authority or replay. Unity documents `fixedDeltaTime` as the fixed-step interval and `timeScale` as global in-game time; a zero scale also suppresses `FixedUpdate` and `WaitForSeconds` ([Time and frame rate management](https://docs.unity3d.com/2022.3/Manual/TimeFrameManagement.html), [Time.timeScale](https://docs.unity3d.com/6000.0/ScriptReference/Time-timeScale.html)). A fixed tick alone will not make `NavMeshAgent` movement deterministic; keep navigation behind an adapter and test the authoritative state separately. |
| Projectile damage decoupled from `ArrowFlight` | **Valid, high priority** | Attackers pass rolled damage into `VisualFactory.Arrow`, and `ArrowFlight.Update` applies the damage only when its visual flight reaches the target ([VisualFactory.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/VisualFactory.cs#L123), [VisualFactory.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/VisualFactory.cs#L143)). A source can die after firing while the presentation object owns the pending hit. Emit a simulation shot/impact event at the tick, then let a render-only projectile consume that event. |
| Spatial acquire and no nested pressure scans | **Valid, high priority** | `Soldier.Acquire` scans every target, then scans every unit again to count pressure for each candidate ([Soldier.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/Soldier.cs#L117)). Towers scan all session targets ([DefenseTower.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/DefenseTower.cs#L96)), and ships scan their world list ([Ship.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/Ship.cs#L106)). Add a deterministic broad-phase grid or buckets with a stable iteration order. It should serve acquisition, pressure, and later fog queries. |
| Remove per-frame allocations in `CityClaim`, population, and HUD income | **Valid** | Each city filters and materializes two lists every `Update`, then orders candidates ([CityClaimZone.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/CityClaimZone.cs#L24)). `BattleSession.Population` uses LINQ `Count` and is called from the main loop and AI ([BattleSession.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/BattleSession.cs#L47)). `BattleHud` performs repeated `Count`, `Where`, `Sum`, `FirstOrDefault`, and creates styles during `OnGUI` ([BattleHud.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/BattleHud.cs#L36), [BattleHud.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/BattleHud.cs#L154), [BattleHud.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/BattleHud.cs#L306)). Replace hot-path LINQ with retained buffers/counters and update HUD aggregates on state changes. |
| Pools | **Valid** | Combat visuals allocate a primitive and an `ArrowFlight` for every shot and allocate another primitive for every impact ([VisualFactory.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/VisualFactory.cs#L123), [VisualFactory.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/VisualFactory.cs#L136)). Units and ships are created with `new GameObject`, while deaths destroy objects ([BattleSession.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/BattleSession.cs#L91), [NavalWorld.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/NavalWorld.cs#L70), [Soldier.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/Soldier.cs#L232)). Pool presentation effects first; pool unit/ship shells only after ownership and lifecycle state are separated from GameObjects. |
| Deterministic IDs | **Valid gap, with one important partial success** | No explicit runtime entity ID exists. `GetInstanceID()` affects avoidance priority and animation phase ([Soldier.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/Soldier.cs#L39), [Soldier.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/Soldier.cs#L161)), and iteration order over Unity objects/lists is not a network identity. The seeded `StartingAllocation` is deterministic and engine-independent ([StartingAllocation.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/Core/StartingAllocation.cs#L49), [StartingAllocation.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/Core/StartingAllocation.cs#L167)), while combat uses a seeded `System.Random` held by the session ([BattleSession.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/BattleSession.cs#L44)). Add explicit monotonic IDs, stable command ordering, and a documented random stream; do not claim full determinism from the current seed. |
| Core assembly definition | **Partly complete / architecture gap remains** | `RiskAI.Runtime.asmdef` already exists and references Navigation and Input System ([RiskAI.Runtime.asmdef](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/RiskAI.Runtime.asmdef#L1)). The `RiskAI.Core` rules, economy, and profiles currently live under that runtime assembly, so the presence of a runtime asmdef is not the same as a Unity-independent Core boundary. A separate Core assembly should remain free of Unity presentation/navigation dependencies and be referenced explicitly by runtime and tests. |
| Remove unused packages and template residue | **Cleanup applied with bounded evidence** | Visual Scripting, Timeline, and Collab Proxy had no runtime/editor source or asset use; their manifest entries were removed. Unity regenerated the default Timeline type name in SceneTemplateSettings; this editor metadata remains without the package. The active build scene is LasMarcas; the stale SampleScene template, its unreferenced profile, Readme asset, and TutorialInfo files were removed after reference searches. URP render-pipeline assets were retained. The template application IDs now use `com.lveillard.riskai` in ProjectSettings and `RiskProjectSetup.Prepare` ([cleanup evidence](ARCHITECTURE-CLEANUP-v0.11.md)). Unity Package Manager regenerated the lockfile; explicit Animation, ParticleSystem, and Audio built-in modules were restored because project scripts still use them after Timeline removal. EditMode validation is 26/26 and PlayMode is 64/64; see [final validation](VALIDATION-v0.11.md) for the build and Player checks. This cleanup makes no performance claim. |
| Data profiles, including ships | **Valid gap** | Units and the tower are static readonly code profiles ([ReforgedProfiles.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/Core/ReforgedProfiles.cs#L19)). Ship health, speed, capacity, damage, range, cooldown, cost, and training time are hard-coded in `Ship` and `Harbor` ([Ship.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/Ship.cs#L26), [Ship.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/Ship.cs#L32), [Harbor.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/Harbor.cs#L78)). `MapLayout` also owns authored city/country arrays ([MapLayout.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/MapLayout.cs#L20)). Move balance data behind pure profile records with a data adapter; include ship profiles and keep the current code defaults as the initial fixture. |
| HUD Toolkit, Input Actions, Addressables, baked NavMesh | **Valid staged migrations** | `BattleHud` is an immediate-mode `OnGUI` HUD, with no HUD Toolkit/UIDocument usage ([BattleHud.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/BattleHud.cs#L36)). `InputSystem_Actions.inputactions` exists and is registered in EditorBuildSettings, but gameplay polls `Keyboard.current` and `Mouse.current` directly ([RtsController.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/RtsController.cs#L21), [EditorBuildSettings.asset](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/ProjectSettings/EditorBuildSettings.asset#L11)); no PlayerInput or generated action wrapper is used. Unity's Input System does support action maps and control schemes ([Input Actions](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.14/manual/Actions.html), [Input Action assets](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.14/manual/ActionAssets.html)), so the asset is a useful migration starting point. Addressables are absent from the manifest and source. NavMesh is built at runtime with `NavMeshSurface.BuildNavMesh`; both scenes have no serialized NavMeshData ([RiskBootstrap.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/RiskBootstrap.cs#L33), [LasMarcas.unity](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scenes/LasMarcas.unity#L99)). Treat these as staged adapters, not completed platform architecture. |
| AI commander | **Valid gap** | AI is a single `RunAi` method on `BattleSession`, mixing recruitment, construction, target choice, and formation orders ([BattleSession.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/BattleSession.cs#L108)). Extract a commander interface that consumes a snapshot and emits commands after the fixed tick exists. |
| PlayerId and fog of war | **Valid gap** | Ownership is represented by raw team integers ([CombatTarget.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/CombatTarget.cs#L8)), and there is no PlayerId or per-player visibility state. `RiskBootstrap` enables only global render fog ([RiskBootstrap.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/RiskBootstrap.cs#L59)); this is atmospheric distance fog, not fog of war. Add an explicit player/visibility layer before exposing spectator or network clients. |
| Authoritative server, tablet touch, Android, and Web | **Valid future direction, not current capability** | The README describes a local AI prototype and explicitly says the simulation is not deterministic yet ([RiskAI README](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/README.md#L22)). There is no network transport, server simulation, or server assembly. Unity provides a Dedicated Server build target, but that only supplies a build shape; it does not make this simulation authoritative ([Dedicated Server build](https://docs.unity3d.com/Manual/dedicated-server-build.html)). The action asset contains a Touch scheme, but the active controller is mouse/keyboard polling. ProjectSettings contain Android and WebGL entries, but there is no Android/Web build artifact or platform validation. Earlier blanket statements that mobile Web is unsupported are obsolete for this editor version. Browser memory, graphics, transport and gesture behavior still need a real build/device test. Plan native Android and mobile/desktop Web as separate validated targets, sharing semantic input commands and an authoritative simulation. |

## Capture behavior: deliberate v0.11 change

The requested capture change is a gameplay decision and should be treated as an intentional contract update. The current code already retains a defender in the claim square and marks an opposing occupant as contested ([CityClaimZone.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/CityClaimZone.cs#L28)). It also has tests that require a living defender to block an enemy ([CityClaimTests.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Tests/PlayMode/CityClaimTests.cs#L78)). However, there is no short conversion timer: `Settlement.Update` and `Harbor.Update` reset capture progress to zero every frame, and ownership changes immediately when `ClaimZone.Step` returns the opposing team ([Settlement.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/Settlement.cs#L153), [Harbor.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/Harbor.cs#L84)).

The current tower rule also deliberately differs from the requested v0.11 rule. `DefenseTower.ChangeOwner` changes the tower team only when the tower is already dead ([DefenseTower.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Scripts/DefenseTower.cs#L78)), and an existing regression test asserts that a captured town keeps the enemy tower until it is destroyed ([BattleIntegrationTests.cs](https://github.com/lveillard/riskai/blob/d0954e1/RiskAI/Assets/RiskAI/Tests/PlayMode/BattleIntegrationTests.cs#L174)). The v0.11 implementation should retain the garrison/blocking behavior, add a short conversion timer that pauses while contested, flip the tower with the host when ownership commits, and update these tests to the new contract. The same state machine should be shared by mainland towns and island harbors.

## Architecture choice and sequencing

Use staged adapters around a small authoritative state model:

1. **P0 — simulation contract.** Add a 20 Hz accumulator and simulation-local pause; move economy, capture, orders, combat timing, and AI decisions onto ticks. Keep rendering and camera updates on frame time. Record command order and explicit entity IDs. Do not promise deterministic `NavMeshAgent` paths; navigation remains a presentation/movement adapter until a server-safe movement model is selected.
2. **P0 — combat and queries.** Resolve shots and area damage as simulation events, then drive projectile visuals from those events. Add a deterministic spatial index for local target queries and replace nested pressure scans.
3. **P0 — capture contract.** Implement retained garrison, owner-unit blocking, conversion timer, and host/tower flip together. Replace the immediate-capture and surviving-enemy-tower tests.
4. **P1 — allocation and lifetime.** Remove hot-path LINQ/list churn, cache population and HUD aggregates, then pool projectile/impact visuals. Pool gameplay shells only after identity and state ownership are explicit.
5. **P1 — assembly and data seams.** Finish the separate Core assembly, move unit/tower/ship data into profile records/assets, and load the initial fixture through an adapter. Keep the deterministic starting-allocation LCG as a tested pure function.
6. **P2 — presentation/content.** Migrate the HUD to UI Toolkit, bind the existing action asset through an input adapter, and add touch-specific command gestures. Add Addressables only with a content lifetime plan; it is not a prerequisite for the simulation split.
7. **P2 — map, AI, and visibility.** Extract the AI commander, add PlayerId/fog state, and decide whether the authored terrain is stable enough to ship baked NavMesh data. Runtime baking currently keeps the map convenient for tests but couples startup to Unity navigation.
8. **P2 — platforms and authority.** Build a headless server target, transport/replication layer, Android player, and desktop Web build as separate validation targets. Use WebSockets or a service appropriate to browser networking rather than assuming desktop socket behavior; validate Web memory, input, and browser focus rules with a real build.

## Package and template cleanup decision

The bounded cleanup is recorded in [`ARCHITECTURE-CLEANUP-v0.11.md`](ARCHITECTURE-CLEANUP-v0.11.md). Unity Package Manager regenerated the lockfile after the manifest cleanup. The explicit Animation, ParticleSystem, and Audio built-in modules remain because project scripts still use those APIs after Timeline removal. `com.unity.pipeline` remains pending because it is experimental and has no source references, but its removal should be validated separately with the target Unity editor. Rider, Visual Studio, and UGUI remain because they are editor/tooling or resolved dependencies; AI Navigation, Input System, URP, and Test Framework have direct evidence. No reference, map, build folder, or active scene was deleted, and no performance improvement is claimed without a measurement.

## Validation performed

The audit used repository-wide text/reference searches and line-numbered source inspection for runtime code, tests, scenes, package manifest/lockfile, and ProjectSettings. The bounded cleanup changed only package/project-settings/template hygiene; no gameplay code was changed by this audit. Unity Package Manager regenerated the lockfile and the project compiled after the three explicit built-in modules were restored; EditMode validation passed 26/26. PlayMode validation remains in progress, and no performance benchmark or build result is claimed here. Shared-worktree gameplay and Core assembly changes belong to the other implementation stream and were left untouched.
